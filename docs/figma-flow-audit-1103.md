# 1103 설계 파일과 MVP_Web 흐름 점검

점검일: 2026-11-09 (한국 시간)

> 후속 반영 (2026-11-09): 요청에 따라 V5-01~V5-04와 진입 분기 UI를 수정했다. A3의 안내/이름 검색 역할과 연결을 복원했고, V5-01e·15초 탐색 제한·큰 글씨 도움 카드·매장 대기 정보 영역을 추가했다. 진입 구간의 현재 기준은 [Figma 흐름 대응표](figma-flow.md#현재-진입-흐름--1103-설계-반영-2026-11-09)를 참고한다. 아래 내용은 **수정 전 점검 기록**이다. 옵션 선택·결제·픽업 부분의 차이는 이번 진입 수정 범위에 포함하지 않았다.

> 추가 요청 반영: START에서 실제/데모 매장 찾기를 선택하도록 변경했다. 실제 선택은 클릭 즉시 Bluetooth 기기 선택을 시작하고, 데모는 Bluetooth 없이 약 2초 후 목록을 표시한다. 탐색 화면의 별도 Bluetooth 버튼은 제거했다. 픽업 뒤에도 START로 돌아가므로 A5의 데모 온보딩 반복은 현재 발생하지 않는다.

## 결론

**부분 일치한다.** 주문의 큰 순서, 매장별 재주문, 메뉴를 담은 뒤 메뉴 목록으로 복귀, 장바구니 옵션 수정 후 복귀는 맞는다. 다만 1103 설계의 기본 옵션 간소화 흐름이 기본으로 적용되지 않았고, 매장 미탐색 안내와 이름 검색 화면의 역할·연결이 달라졌으며, 결제 취소·실패 후 바로 재결제하는 선택지가 없다.

기존 `figma-flow.md`는 이번 파일에 없는 09 페이지를 기준으로 작성되어 있으므로, 그 문서의 ‘반영’ 표기만으로 1103 설계와 일치한다고 판단할 수 없다.

이 점검에서는 앱 코드를 수정하지 않았다.

## 설계 내부에서 먼저 구분해야 하는 부분

08 페이지의 본 흐름에는 `V5-06 → V5-07(담기 완료) → V5-08`이 남아 있다. 하지만 같은 페이지의 설명 (`216:2237`)은 본 흐름이 V4 화면이며, 피드백 반영 사항은 별도 ①~③ 섹션에 있다고 명시한다.

② 복잡성 개선에서는 다음을 명시한다.

- 기본 옵션을 미리 선택하고 바꿀 때만 옵션 변경으로 들어간다 (`214:1573`).
- 기존 담기 완료 화면을 없애고 메뉴로 돌아와 담음 안내와 장바구니 바를 제공한다 (`214:1578`).
- 매장 주문 이력이 있을 때 옵션·담기·장바구니를 건너뛰어 결제한다 (`214:1568`).

따라서 **현재 앱에 V5-07이 없다는 이유로 누락이라고 판정하지 않았다.** 다만 온도 필수 선택을 기본으로 둘지, 기본 옵션 요약을 기본으로 둘지는 본 화면과 보완안의 차이이며, 현재 앱은 이번 파일에 없는 09 페이지 쪽 결정을 따르고 있다.

## 주요 차이

### A1. 우선순위 높음 — 구현 기준이 요청 파일과 다르다

- 설계: 이번 파일은 08 페이지까지 존재한다.
- 현재 문서: `figma-flow.md:5`는 다른 이름의 원본과 09 페이지 interaction을 기준으로 삼는다고 설명한다. `:37`에서는 그 09 페이지를 이유로 기본 옵션 요약을 선택 설정으로 둔다.
- 영향: 기능이 누락됐는지, 이전 설계를 구현했는지, 웹에 맞춰 바꾼 것인지 구별하기 어렵다. 기존 테스트에도 `09:`를 기준으로 한 검증이 다수 있다.
- 제안: 먼저 1103 파일의 보완안을 현재 구현 기준으로 채택할지 정하고, 확정된 기준 파일·페이지·우선순위를 대응표에 명시한다.

### A2. 우선순위 높음 — 옵션을 미리 골라 바로 담는 흐름이 기본이 아니다

- 설계: `V5-06s` (`214:1403`)와 설계 이유 (`214:1573`)는 기본값 요약 → ‘이대로 담기’, 필요할 때만 ‘옵션 바꾸기’를 제안한다. 탭 수 비교 (`214:1550`)도 이 순서를 전제한다.
- 구현: `src/core/flow.ts:18`에서 `quickOptions: false`다. 일반 메뉴 선택은 `selectionFlow` (`:94`)에 따라 기본적으로 `V5-06`으로 간다. `src/core/domain.ts`의 `initialOptions`는 필수 온도를 비워 두므로 사용자가 온도를 골라야 담을 수 있다.
- 조건부 일치: 설정에서 ‘기본 옵션 빠르게 담기’를 켜면 `V5-06s`가 동작한다 (`App.tsx:869`, `:1598`). 옵션이 많은 메뉴는 별도의 단계형 화면이 우선된다.
- 영향: 기능은 있지만, 1103 보완안이 기대하는 기본 주문 경험과 탭 수는 다르다.
- 제안: 보완안을 채택한다면 기본값 흐름을 기본으로 바꾸고, 직접 옵션 선택 경로를 보조 행동으로 둔다. 온도를 의무 확인하도록 유지하려면 설계의 기본 흐름과 탭 수 설명을 함께 수정한다.

### A3. 우선순위 높음 — ‘매장이 없어요’ 안내와 이름 검색의 역할·연결이 다르다

- 설계: `V5-02 → V5-02e(찾는 매장이 없을 때) → V5-02s(이름으로 찾기) → V5-03`. 화살표는 `216:2279`, `216:2283`, `216:2287`이다.
- 설계의 `V5-02e` (`216:2132`): 다시 찾기, 이름으로 찾기, 주변 사람에게 도움 요청이라는 세 가지 해결 방법을 제시한다.
- 설계의 `V5-02s` (`216:2147`): 입력창과 근처 참여 매장 검색 결과를 제공한다.
- 구현: `App.tsx:577`에서 ‘찾는 매장이 없어요’를 누르면 `V5-02s` 안내로 간다. 안내의 ‘매장 이름으로 찾기’는 `V5-02e` 검색으로 연결된다 (`:487`, `:500`, `:532`). `src/ui/content.ts:15`도 이 역할로 제목을 정의한다.
- 영향: 사용자는 안내 → 검색 → 선택을 할 수 있지만 화면 ID의 의미가 뒤바뀌었고, 원본의 3개 해결 행동을 모은 안내 화면은 동일하게 구현되지 않았다. 공통 ‘직원 도움’은 일반 주문 도움 대화상자다 (`App.tsx:1333`).
- 제안: ID만 바꾸는 문제로 처리하지 말고 안내에 필요한 행동을 복원한 뒤, 이름 검색과 안내를 설계의 역할에 맞춰 연결한다.

### A4. 우선순위 중간 — 결제 취소·실패 후 바로 재결제하는 버튼이 없다

- 설계: `V5-09c` (`216:2201`)와 `V5-09f` (`216:2217`) 각각에 ‘다시 결제하기’와 ‘장바구니로 돌아가기’가 있다. 버튼 근거는 `216:2211~2212`, `216:2230~2231`이다.
- 구현: 기능상 대응 화면은 `P02-C`, `P02-F`다. `App.tsx:1108`부터 결제 준비 오류·취소·실패·시간 초과를 묶어 ‘장바구니로 돌아가기’ 하나만 표시한다. `RETRY_PAYMENT`도 장바구니로 이동한다 (`src/core/flow.ts:555`).
- 영향: 다시 결제하려면 장바구니로 돌아가 결제 버튼을 한 번 더 눌러야 한다. 담은 메뉴는 유지된다.
- 제안: 결과가 취소/실패로 확정된 경우에만 바로 재결제 경로를 제공한다. 결과 불명확 상태 `P02-V`는 기존 결제를 먼저 조회하는 현재 동작을 유지한다.

### A5. 우선순위 낮음 — 데모에서는 픽업 뒤 첫 사용 안내가 다시 나온다

- 설계: 온보딩은 처음 실행할 때만 나오고, 설정에서 다시 듣기를 제공한다 (`213:1447`).
- 구현: `src/core/flow.ts:559`의 `PICKUP_COMPLETE`는 데모 탐색·데모 주문이면 `onboarded: true`가 유지되어도 `V5-O1`로 보낸다. 일반 경로는 매장 탐색으로 돌아간다. 기존 테스트도 이 데모 동작을 명시적으로 기대한다 (`tests/flow.test.ts:127`).
- 영향: 데모를 반복하면 신규 사용자 안내를 매번 다시 지나가게 된다.
- 제안: 반복 시연을 위한 의도라면 데모 동작으로 명시하고, 실제 첫 사용 규칙과는 구분한다.

## 추가된 복구 흐름

가격 변경 확인 `P01-E1`, 결제 준비 오류 `P01-E2`, 시간 초과 `P02-T`, 결과 불명확 `P02-V`와 진행 중 결제 복원은 1103의 본 화살표보다 상세하다. 이는 추가 구현으로 분류했다. 특히 결과가 불명확할 때 기존 요청 키로 확인하는 처리는 새 결제를 만드는 경로와 구분해야 한다.

## 검증 결과와 한계

- `npm test`: 3개 파일, 20개 테스트 통과.
- `npm run typecheck`: 통과.
- 기존 테스트는 구현의 상태 전이·결제 동작을 확인한다. 1103 원본을 읽어 기대값을 생성하는 설계 적합성 테스트가 아니므로, 전부 통과해도 위 차이는 남는다.
- 실제 화면 점검을 위해 별도 로컬 포트로 서버를 실행했지만, 브라우저 연결 호스트를 사용할 수 없었다. 이후 Windows UI 도구도 현재 브라우저 URL을 충분히 식별할 수 없다는 이유로 자동 중단되어 UI 점검을 진행하지 않았다. 임시 서버는 종료했다.
- 따라서 본 문서는 **설계 원본과 코드의 정적 대조 + 기존 자동 테스트** 결과다. 실제 버튼 클릭 재현, 브라우저별 Bluetooth·음성·진동, 외부 결제 서버, 화면 꺼짐 알림, 화면 배치의 시각적 일치 여부는 검증하지 않았다.

## 권장 반영 순서

1. 기준을 1103 파일의 V5 보완안으로 확정할지 결정하고 `figma-flow.md`의 기준을 정리한다.
2. 옵션 기본값 흐름을 기본으로 둘지 결정한다. 이 결정이 핵심 주문 단계 수를 바꾼다.
3. 미탐색 안내 → 이름 검색 → 매장 확인의 화면 역할과 버튼 연결을 맞춘다.
4. 취소/실패가 확정된 경우의 바로 재결제 버튼을 복원한다.
5. 웹의 매장 탐색·결제 창 진입·알림 제한을 설계에 명시하고, 사용자가 보는 문구를 실제 동작에 맞춘다.
6. 데모 온보딩 반복과 진동 패턴 같은 나머지 차이를 정리한 뒤 실제 브라우저에서 흐름을 재검증한다.
